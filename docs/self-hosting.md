# Самостоятельное развёртывание

## Подготовка

Используйте сервер с Docker и Compose v2, собственный домен и HTTPS reverse proxy. Скопируйте `.env.example` в `.env`, ограничьте права (`chmod 600 .env`) и задайте:

- `POSTGRES_PASSWORD`: уникальный случайный пароль (для текущего DATABASE_URL используйте URL-safe символы).
- `PUBLIC_ORIGIN`: точный HTTPS origin без завершающего `/`.
- `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME`: собственный бот из BotFather.
- `AUTH_CODE_SECRET` и `TELEGRAM_WEBHOOK_SECRET`: два разных случайных секрета, например каждый через `openssl rand -hex 32`. Даже в polling заполните оба.
- `OWNER_TELEGRAM_ID`: проверенный числовой ID владельца, не username и не ID бота.
- `TELEGRAM_DELIVERY_MODE=polling`: исходящее получение сообщений, не требует входящего Telegram webhook.
- `APIFY_TOKEN`: для платного импорта; не требуется для просмотра лендинга и входа.

Никогда не вставляйте токены в README, команды с публичными логами или Git. Не используйте production-секреты в CI.

Для проверки ID до запуска polling/webhook отправьте своему боту уникальную случайную фразу. Оператор получает update через Bot API, проверяет приватный чат, саму фразу и `message.from.id`, затем сохраняет этот ID только в `.env`. Не назначайте владельцем первого зарегистрировавшегося. Не используйте сторонних ботов для передачи токена.

## HTTPS и запуск

Compose публикует только внутренний HTTP на `127.0.0.1:3300`. Например, Caddy, запущенный **на хосте**, принимает HTTPS:

```caddyfile
hype.example.com {
    reverse_proxy 127.0.0.1:3300
}
```

Замените домен своим и направьте DNS на сервер; освободите порты 80/443 для внешнего прокси. Если прокси работает в Docker, настройте отдельное соединение с ingress-сетью приложения: `127.0.0.1` внутри контейнера не является хостом. В комплекте нет настроек чужого VPS или общей внешней Docker-сети.

```bash
docker compose up -d --build
docker compose ps
curl --fail https://hype.example.com/api/health
```

Интерфейс, `/api` и защищённые `/media` остаются на одном origin. Не раздавайте пользовательские медиа напрямую через Nginx. Не отключайте Secure cookie, CSRF или авторизацию для обхода проблем HTTPS.

В режиме polling один обработчик выбирается PostgreSQL advisory lock; повторные `update_id` учитываются в БД. Для webhook смените режим на `webhook` и зарегистрируйте через Telegram Bot API `setWebhook` адрес `https://<ваш-домен>/api/telegram/webhook` с `secret_token`, равным `TELEGRAM_WEBHOOK_SECRET`. Не запускайте оба режима одновременно. Переход на polling удаляет webhook без сброса ожидающих updates.

Проверьте реальный сценарий: `/login` → Start → код из браузера → подтверждение в боте → возврат в исходный браузер → выход. Ссылка в Telegram не переносит сессию между браузерами.

## Импорт и переводы

Apify оплачивается отдельно. В `.env.example` заданы actor IDs, лимиты количества материалов и стоимости запуска. Начните с одного собственного тестового источника; не запускайте массовый импорт для проверки установки.

Переводы используют прямой Responses API Yandex AI Studio без CLI. Задайте на сервере AI_PROVIDER=yandex, YANDEX_AI_API_KEY, YANDEX_AI_FOLDER_ID, YANDEX_AI_MODEL=aliceai-llm и YANDEX_AI_ENABLED=true только после проверки доступа и оснований передачи текстов. OPENAI_ENABLED оставьте false; автоматического fallback нет. Без ключа или явного включения API ничего не отправляет. TRANSLATION_AUTO_START включает перевод новых импортов. Настройки таймаута и размера запроса сохраняют существующие имена OPENAI_TIMEOUT_SECONDS, OPENAI_MAX_INPUT_CHARS, OPENAI_MAX_OUTPUT_TOKENS; параметры пакетов и дневных квот — TRANSLATION_*. Ответ имеет строгую JSON Schema, store=false и x-data-logging-enabled=false; инструменты и автоматические повторные платные запросы не включены. Это не обещание отсутствия всех технических журналов у провайдера. До подключения библиотека и ручное редактирование доступны.

Для своего публичного экземпляра замените контакты, реквизиты, название и продуктовые тексты в `ui/landing.js` и документах `legal/`. Для Яндекс ID задайте YANDEX_CLIENT_ID и зарегистрируйте https://<ваш-домен>/api/auth/yandex/callback с правами login:info и login:email. Используется PKCE S256 без Client Secret. Для привязки Яндекса к старому аккаунту сначала войдите текущим способом, затем в течение 5 минут откройте профиль → «Вход и безопасность» → «Подключить».
Адрес Яндекса отображается в профиле с пометкой «Из Яндекс ID». Внешний HTTPS-прокси должен сохранять Referrer-Policy: no-referrer, чтобы адрес OAuth callback не передавался при переходе.

## Email-код

Задайте только на сервере `UNISENDER_GO_API_KEY`, подтверждённый `EMAIL_FROM_ADDRESS` и `EMAIL_FROM_NAME`. Настройте SPF/DKIM отправителя в Unisender Go. Ключ API не передаётся браузеру. Шесть случайных цифр действуют 5 минут, доступны 5 попыток, повторная отправка через 60 секунд. Код хранится через HMAC с AUTH_CODE_SECRET и привязан к исходному браузеру; session cookie выдаётся только после проверки. Лимиты адреса, браузера, сетевого адреса и общего объёма работают в PostgreSQL. `EMAIL_HOURLY_LIMIT=100` ограничивает общий объём; остальные настройки — в `.env.example`. Это однофакторный passwordless-вход.

Разрешён точный список сервисов в `backend/app/email_auth.py`, включая Mail.ru, Яндекс и Рамблер, а не любые адреса `.ru`. После подтверждения кода открывается существующая email identity или единственный аккаунт с совпадающим `default_email` из Яндекс ID. Во втором случае создаётся email identity этого аккаунта. Если совпало несколько аккаунтов, вход отклоняется; данные не объединяются. Новый адрес создаёт отдельный пустой аккаунт. До проверки кода наличие аккаунта не раскрывается. Миграция `0010_email_auth` не меняет существующих пользователей и их данные.

## Обновление и резервные копии

Перед каждым обновлением сделайте закрытую резервную копию PostgreSQL:

```bash
umask 077
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backup.dump
test -s backup.dump
git pull --ff-only
docker compose up -d --build
```

Дополнительно сохраняйте `media_data`, секреты `.env`. Дамп БД не содержит файлов медиа. Не загружайте резервные копии в Git.

API применяет `alembic upgrade head` при старте. Миграция `0007_accounts` останавливается, если существующие данные требуют переноса, а `OWNER_TELEGRAM_ID` не задан. Старые записи закрепляются за проверенным владельцем, не за первым посетителем. После миграции проверьте количество записей, связи и доступ владельца. Не откатывайте только код на версию без авторизации. Восстановление БД и медиа выполняйте на остановленном приложении из согласованной резервной копии.

## Проверки

`npm test` проверяет frontend. Из `backend/` команда `python -m pytest -q` запускает серверные тесты. Для PostgreSQL-проверок нужна **отдельная одноразовая тестовая БД**, не production:

```bash
export DATABASE_URL='postgresql+psycopg://test_user:test_password@127.0.0.1:5432/hype_test'
python -m alembic upgrade head
python -m pytest -q
AUTH_PG_TEST_URL="$DATABASE_URL" python -m pytest -q tests/test_auth.py
```

Тесты могут изменять и очищать тестовые таблицы. Шаблон `docs/ci.yml` повторяет этот сценарий с временным PostgreSQL. Для включения скопируйте его в `.github/workflows/ci.yml` и загрузите с разрешением GitHub `workflow`; пока он не активен. Перед открытием регистрации проверьте двумя своими аккаунтами изоляцию источников, черновиков, заданий и медиа. Проверка health не заменяет реальный вход.
