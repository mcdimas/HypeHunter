# Повторяемая проверка Hype Hunter

## Запуск

Один раз: `npm ci`, установка `backend/requirements-dev.txt` в `.venv`, `npx playwright install chromium`.

- `npm run test:release` — frontend, backend, затем сквозные браузерные тесты.
- `npm run test:e2e` — только реальные браузерные сценарии (Chromium desktop и мобильный viewport).
- `npm run test:production` — безопасная проверка опубликованного сайта без входа и записей.
- `npx playwright show-report` — отчёт; ошибки сохраняют screenshot и trace в игнорируемые каталоги. Не публиковать отчёты с реальными сессиями/контактами.

Linux использует `python`, Windows — `.venv/Scripts/python.exe`. Переопределение: `E2E_PYTHON` (абсолютный путь). Серверы занимают 8001/4174; существующие процессы не переиспользуются. Playwright сам запускает и останавливает оба сервера. Тестовый TLS-сертификат создаётся на один день в `work/e2e`, исключён из Git; игнорирование сертификата только в тестовой конфигурации loopback, не в production.

Обычный `test:release` принудительно использует SQLite, не наследует URL PostgreSQL для тестов. Отдельные PostgreSQL-прогоны в CI допускают только loopback и БД с именем `*_test` или `test_*`; production-URL отвергается до сбора тестов.

Сквозные тесты используют реальный FastAPI, авторизацию/CSRF, БД, импортную нормализацию и обработчик платежей. Только внешние сервисы заменены фикстурами. Никакой production-фикстуры, тестового входа или отключения серверной защиты не добавлено. Сетевые обращения наружу запрещены в backend tests и E2E; на браузерной стороне provider checkout заменён тестовой страницей. Обычный прогон не расходует AI/Apify-лимиты и не отправляет письма/деньги/чеки.

## CloudKassir: обязательные проверки после подключения

Интеграция пока отсутствует, поэтому её результаты **не помечены как прошедшие**. Существующая выдача доступа после оплаты и подготовка данных для владельца уже проверяются. До подключения сохраняется ручной чек НПД.

После подтверждения провайдером поддержки вашей схемы НПД и выбора API добавить тесты фактического адаптера:

1. Подтверждённая успешная оплата запускает один чек с серверной суммой, услугой, email и ИНН; pending/canceled не запускают чек.
2. Дубли payment webhook, повторный запуск и параллельные задачи не создают второй чек.
3. Таймаут/429/5xx → сохранённая задача и безопасный повтор с тем же ключом; после неизвестного результата сначала сверка, не слепое повторное создание.
4. Ответ принят не равен фискализирован: состояния отдельно от оплаты; ошибки кассы не удаляют подтверждённый платёж и не начисляют доступ повторно.
5. Уведомления проверяются способом, предусмотренным API; подделанные, старые, чужие события отклоняются. Сумма/email/ИНН не принимаются из недоверенного webhook.
6. Частичный/полный возврат → корректный отдельный чек возврата без повторов; оригинальный чек сохраняется.
7. Клиент видит только собственный чек, владелец видит статус/ошибку; секреты не оказываются в логах или браузере.

Не писать фиктивные «зелёные» тесты несуществующего CloudKassir-адаптера. Живой тест фискализации — отдельно согласованный, не на каждом коммите.

## Релизный барьер

CI сначала выполняет frontend, backend, миграции и гонки PostgreSQL, затем Playwright; при ошибке деплой не начинается. Все зелёные автоматические проверки не заменяют ручной тест реального внешнего OAuth, доставки почты, оплаты и фискализации после изменения этих интеграций. Полная проверка перевода с живым API запускается только по явному запросу и на заранее ограниченном наборе, а не внутри `test:release`.
